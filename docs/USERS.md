# Users 360 and blocking — Phase 2 contract (follows `docs/DASHBOARD_REVAMP.md` §5.3; builds on `docs/RELEASES.md` and `docs/ROLES.md`)

Today the Users tab loads every devotee at once and offers block / delete; a blocked person is just signed out with a generic message. This phase makes a
user a first-class record an operator can understand and act on, and makes blocking **explain itself**.

## 0. Principles
1. **Server-side everything**: search, filters and paging are done by the API (the list must work with 100 000 users), never by loading all rows.
2. **Say why**: a block carries an internal reason (operators only) and a **message the user reads** (EN + HI); the app shows it. No generic "error".
3. **Honest partial results**: the 360 view fans out to other services with short timeouts; a slow/down service shows "unavailable" for its tab, never blocks the page or fakes data.
4. **Privacy by the existing rules**: devotee identity stays masked for roles without `devotees:view` (area unchanged; custom roles may be granted it); exports are `devotees:edit` + audited; no secrets, no tokens, no raw push tokens in any response.
5. Every write is audited (with before/after of the block state, tags, notes).

## 1. Model additions (identity service)
```
User (existing) + {
  block: { active: bool, scope:'account', reason (≤ 300, internal), message (≤ 300, shown to the user), messageHi (≤ 300), until: date|null,
           at, by (operator username) }|null,            // `blocked` (bool) stays and is kept = block.active && (until null or in the future)  — existing readers keep working
  blockHistory: [ { action:'block'|'unblock'|'auto_unblock', at, by, reason, message, until } ]   // last 20
  tags: [string]  (≤ 10, each ≤ 24, lowercase slug-ish),   notes: [ { id, text (≤ 500), by, at } ] (last 50, newest first) }
BlockedDevice { deviceId* (unique), reason (internal), message, messageHi, until|null, at, by }          // device-level block (stops re-registration abuse)
```
Auto-unblock: a block with `until` in the past is treated as not blocked immediately (every check compares the date) and a sweeper writes the `auto_unblock` history row.

## 2. Identity admin API (via admin BFF; area `devotees`: view/edit)
* `GET /api/admin/users?q=&status=all|active|blocked&tag=&role=&versionCode=&lastActiveBefore=&lastActiveAfter=&createdFrom=&createdTo=&sort=lastActive|createdAt|name&dir=&limit=(default 50, max 200)&cursor=` → `{ users:[UserRow], next, total|null }`. `q` matches name, phone, email, uid prefix (case-insensitive, indexed prefix/regex-safe; the phone/email are matched on the stored normalised values). `UserRow = { id, uid, name, contact (masked for roles without devotees:view), method, role, blocked, blockUntil, tags, lastActive, createdAt, versionName?, versionCode?, hasPush }` (version/push from the devices registry in one batched lookup). `total` may be `null` when expensive (the UI says "many"). The old unpaginated `GET /api/users` keeps working for one release but is not used by the dashboard.
* `GET /api/admin/users/:id` → the **360 aggregate** `{ user:{profile fields incl. dob, gender, email(+verified), photoUrl, savedTemples count, acceptedPolicies, block, blockHistory, tags, notes}, devices:[{deviceId, versionName, versionCode, osApi, model, platform, firstSeen, lastSeen, blocked}], wallet:{ balance, recent:[txn…] }|{unavailable:true}, bookings:{ total, recent:[…] }|{unavailable}, events:{ registrations:[…], badges:[…] }|{unavailable}, calls:{ total, recent:[…] }|{unavailable}, audit:[recent operator actions about this user] }` — each section fetched in parallel with a **1.5 s** timeout; a failed section is `{ unavailable:true, reason }`. Recent lists ≤ 10 rows, newest first. Masking identical to the list.
* `POST /api/admin/users/:id/block` `{ reason, message, messageHi?, until?(iso|null), alsoBlockDevices?:bool }` → `{ user }`. Requires `reason` and `message` (`400 bad_block {fields}`); `until` must be in the future; the operator cannot block themselves (an operator is not a devotee, n/a) or an astrologer without the same permission; also **revokes the user's Firebase refresh tokens** (existing behaviour) and, with `alsoBlockDevices`, blocks their registered `deviceId`s. Idempotent: blocking a blocked user updates the message/until and writes history.
* `POST /api/admin/users/:id/unblock` `{ note? }` → `{ user }` (also unblocks their devices when asked `{ unblockDevices:true }`).
* `POST /api/admin/users/:id/sign-out` → `{ revoked:true }` (revokes refresh tokens; the app's next token refresh fails and it returns to login) .
* `POST /api/admin/users/:id/tags` `{ add:[…], remove:[…] }` · `POST /api/admin/users/:id/notes` `{ text }` · `DELETE /api/admin/users/:id/notes/:noteId` (own note or `devotees:edit`).
* `GET /api/admin/users/export?…same filters…` → `text/csv` stream (id, uid, name, contact, method, role, blocked, tags, createdAt, lastActive, version) capped at 50 000 rows, **admin-visible only fields** (the CSV is never masked-then-unmasked), audited with the filter and row count.
* `GET /api/admin/blocked-devices` · `POST /api/admin/blocked-devices` `{ deviceId, reason, message, messageHi?, until? }` · `DELETE /api/admin/blocked-devices/:deviceId`.
* **Delete** (existing `DELETE /api/admin/users/:id`) requires the body `{ confirm: "<user's contact or uid last 6>" }` (`400 confirm_mismatch`) and is audited; it still deletes the Firebase account.
* The services behind the 360 expose **internal read-only by-uid routes** if missing (wallet balance + recent txns, orders bookings, events registrations/badges, calls history); callers: identity only; documented in the service docs; no PII beyond what the admin view needs.

## 3. What the phone sees (mobile BFF / identity)
* Every authenticated route already asks identity "is this account blocked?" (fail **closed**). A blocked account now gets `403 { code:'account_blocked', error, message, messageHi, until|null, support:{ email?, phone? } }` (support from the settings table, blank hidden), and `POST /api/auth/sync` for a blocked account returns the same body with 403 (so a blocked user cannot sign back in to a working session). A device block returns `403 { code:'device_blocked', … same shape }` on `/api/auth/sync` and authenticated routes (checked from `X-Device-Id`, cached 30 s in the BFF, **fails open** if the lookup is down — a device block is a deterrent, an account block is the control).
* `until` expiry needs no action: the next check passes.

## 4. App
* A themed **AccountBlockedScreen** (full-screen, EN/HI): the operator's `message`/`messageHi`, "until <date IST>" when set, the support contact buttons when configured, **Sign out** (always available) and **Try again** (re-checks). It replaces today's silent sign-out + "This account has been blocked" error. Triggered by `403 account_blocked|device_blocked` from ANY call or from sign-in, via the same event-bus pattern as the policy gate (single place: the central API client).
* The sign-out action clears local session data as today. A force-signed-out user just lands on login (their refresh token is revoked).

## 5. Dashboard (Users module, `#/people/users`)
* **List**: search box (debounced, server-side), filters (Status, Tag, Role, App version, Last active, Created), sort, column chooser, cursor "Load more" (no full load), selected-row bulk bar (add tag, export selected), **Export CSV** (confirm; audited), saved views stored locally.
* **Detail** (`#/people/users/<id>`, opens as a right-hand drawer from the list and as a full page on deep link): header (avatar, name, masked contact, role, block pill) with actions **Block…**, **Unblock**, **Force sign-out**, **Add note/tag**, **Open wallet** (existing coins/wallet form), **Delete…** (typed confirmation); tabs: **Profile** · **Devices** (version/OS/model/last seen/push, block this device) · **Wallet** · **Bookings** · **Events** · **Calls** · **Activity** (block history + audit rows about the user) · **Notes & tags**. Each fan-out tab shows an "unavailable" state with Retry; skeletons while loading.
* **Block modal**: internal reason (required), **message shown in the app** EN + HI (required EN; counter; a **phone preview** of the Account-blocked screen), end date or "until I unblock", "also block this user's devices" (default off), submit → toast. A blocked user's header shows the active message and "unblock now".
* **Blocked devices** sub-page (list, add, remove). Everything permission-driven (`devotees:view/edit`), read-only without edit, masked as the API returns.

## 6. Tests
Identity: list filters/paging/prefix search, 360 aggregate with a failing/slow section (partial result), block validation + idempotency + history, `blocked` derivation with `until`, auto-unblock, force sign-out, tags/notes limits, export cap + audit row, delete confirm, device block cache + fail-open; BFF: 403 shapes on sync and authed routes, support contact from settings; masking matrix per role; dashboard pure logic (filters→query, block form validation, tab state), app pure logic (blocked-body parsing, screen state).

## Backend as built (binding for the dashboard and the app)
**Routes** (admin BFF paths, all area `devotees`; GET = view, everything else = edit; errors `{ error, code, ... }`):
* `GET /api/admin/users` -> identity `/admin/users/list` -> `{ users:[UserRow], next, total, versionsUnavailable?, versionFilterTruncated? }`. `UserRow = { id, uid, name, contact, method, role, blocked, blockUntil, tags, lastActive, createdAt, versionName?, versionCode?, hasPush }`. `q` is a case-insensitive **prefix** on name, e-mail, contact, uid and phone (a number typed without `+91` also matches); `status all|active|blocked`; `tag`; `role devotee|astrologer`; `versionCode`; `lastActiveAfter|Before`, `createdFrom|To` (a bare `YYYY-MM-DD` is an IST day, `To` inclusive); `sort lastActive|createdAt|name`, `dir`; `limit` 50 (max 200); `cursor` = the previous `next`. `total` only on the first page (no cursor), `null` above 100 000 or when slow. Bad input: `400 bad_filter { fields }`, `400 bad_cursor`. The version filter asks the device registry (up to 5 000 accounts per build; `versionFilterTruncated` says more exist); if the registry is down the filter is refused `503 devices_unavailable`. One batched registry call per page supplies the version columns (down: rows still come, `versionsUnavailable:true`). `hasPush` = the account has an FCM token registered with identity.
* `GET /api/admin/users/:id` -> `{ user, devices, wallet, bookings, events, calls, audit }`. `user = UserRow + { phone, email, emailVerified, photoUrl, bio, gender, dob, savedTemples (count), acceptedPolicies, block, blockHistory[], notes[] }`; `block = { active, scope, reason, message, messageHi, until, at, by } | null` (`active` is true only while it applies now); `blockHistory[] = { action:'block'|'unblock'|'auto_unblock', at, by, reason, message, until }` newest first (last 20); `notes[] = { id, text, by, at }` newest first (last 50). Each fan-out section is `{ unavailable:true, reason }` on failure, `reason` = `timeout | not_configured | forbidden | upstream_error | upstream_forbidden`. `forbidden` = the operator lacks that area's view right (`wallets`, `orders`, `events`, `calls`, `audit`) and the service was not asked. **`devices` is also a fan-out section** (the registry): an array, or `{ unavailable, reason }`.
  Row shapes (each list <= 10, newest first; time fields are ISO strings):
  * `devices[] = { deviceId, versionName, versionCode, osApi, model, platform, firstSeen, lastSeen, hasPush, blocked }` (`hasPush` = an Expo push token is registered on that device).
  * `wallet = { balance, recent:[{ id, type, amount, balanceAfter, refType, at, createdAt }] }` (no notes / operator names).
  * `bookings = { total, recent:[{ id, bookingRef, poojaTitle, title, templeName, packageName, status, totalCoins, coins, poojaDate, createdAt, at }] }` (`title` = `poojaTitle`, `coins` = `totalCoins`; no names/gotra/address).
  * `events = { registrations:[{ eventSlug, title, status, joinedAt, checkedInAt, createdAt, at }], badges:[{ badgeSlug, eventSlug, title, earnedAt, at }] }`.
  * `calls = { total, recent:[{ id, as:'devotee'|'astrologer', with, status, endReason, minutesBilled, coinsCharged, coins, requestedAt, endedAt, at }] }`.
  * `audit[] = { id, at, operator, method, path, summary, status, before?, after? }` (`summary` e.g. `POST block`; needs `audit:view`, else `forbidden`).
* `POST /api/admin/users/:id/block { reason, message, messageHi?, until?, alsoBlockDevices? }` -> `{ user, devicesBlocked }`. `400 bad_block { fields }` with keys `reason | message | messageHi | until | alsoBlockDevices`. Blocking an astrologer also needs `astrologers:edit` (`403 forbidden`, `needs`). Re-blocking updates and adds a history row. Revokes Firebase refresh tokens.
* `POST .../unblock { note?, unblockDevices? }` -> `{ user, devicesUnblocked, unchanged? }` (`unchanged:true`, no history row, when the account was not blocked). `POST .../sign-out` -> `{ revoked:true }` (`{ revoked:false, reason:'firebase_not_configured' }` when identity has no Firebase key; `409 no_uid`). `POST .../tags { add, remove }` -> `{ user }` (`400 bad_tags { fields }`; tags are lowercase slugs, <= 24 chars, <= 10 per person). `POST .../notes { text }` -> `201 { user, note }`; `DELETE .../notes/:noteId` -> `{ user }` (author or `devotees:edit`; the BFF gate itself demands edit for any DELETE).
* `DELETE /api/admin/users/:id { confirm }` (also the old `DELETE /api/users/:id`): `confirm` = the contact (any case) or the last 6 of the uid, else `400 confirm_mismatch`. The old `GET /api/users` (unpaginated) and `PUT /api/users/:id` still answer; a `PUT { blocked:true }` makes a real block with a stock message.
* `GET /api/admin/users/export?<list filters>&ids=<comma list of user ids>` -> `text/csv` (UTF-8 with BOM; columns `id,uid,name,contact,method,role,blocked,tags,createdAt,lastActive,version`; tags joined by `;`; formula-looking cells are prefixed with `'`). Needs `devotees:edit` as well as view. With `ids` only those users (<= 1 000) are exported, the other filters still apply, so the row count equals the number of ids that exist. Capped at 50 000 rows. Identity writes ONE audit row up front (path `/api/admin/users/export`, `after = { export, filter, rows, capped }`). A failure after the first byte aborts the connection (the file is never silently short).
* `GET|POST /api/admin/blocked-devices`, `DELETE /api/admin/blocked-devices/:deviceId`: `{ devices:[{ deviceId, uid, reason, message, messageHi, until, at, by, active }] }`; POST is an upsert (`201` new / `200` changed), same `bad_block` validation plus `deviceId`.
* Writes carry audit before/after in `X-Audit-Detail`: block/unblock `{ blocked, until, reason, message, messageHi (+ devicesBlocked|devicesUnblocked) }`, tags `{ tags }`, notes `{ note }`, delete `{ role, blocked, tags }`, devices `{ deviceId, reason, message, messageHi, until }`.

**What the phone sees**: `403 { error, code:'account_blocked'|'device_blocked', message, messageHi, until|null, support:{ email?, phone? } }` (`messageHi` may be `''` when the operator wrote English only; the internal `reason` never leaves identity). Served on `POST /api/auth/sync` and every non-public route; the monolith's public routes (content, flags, ...) stay open. Account check: cached 10 s, fail closed. Device check (`X-Device-Id`): cached 30 s, fail open; an account block wins. `support` comes from the `supportEmail` / `supportPhone` settings (cached 60 s).

**Contract notes / problems**: (1) Masking is implemented (pseudonym `Devotee ••NNNN`), but every Users route already requires `devotees:view`, so no caller can currently receive a masked row; the practical matrix is per 360 section (above). (2) `devices` in the 360 became a possibly-unavailable section, not a bare array. (3) The version filter is bounded (5 000 accounts per build). (4) Timed blocks stop applying the instant `until` passes; the stored `blocked` flag and the `auto_unblock` history row follow within `BLOCK_SWEEP_EVERY_MS` (60 s). (5) Existing `blocked: true` rows are migrated at boot into a real block (reason "Blocked before block reasons were recorded", stock message, by `migration`).
