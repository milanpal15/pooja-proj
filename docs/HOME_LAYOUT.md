# Home layout v2 — fully server-driven Home (contract)

Authoritative contract. The catalog service, the BFFs, the dashboard and the app are built against THIS file; if an
implementation must differ, change this file in the same commit. Supersedes the "fixed layout" part of
`docs/POOJA_AND_HOME.md` §1b (the Home slider, `HeroSlide`, stays and is referenced by the `slider` block).

> **Status (backend):** built and tested in the catalog service + both BFFs (see "Implementation notes" at the end). Dashboard and app are separate work.

## 0. Principles
1. **The whole page is data.** Header, search, slider, grids, shelves, panchang, floating button — every band of Home is a
   *block* in one ordered JSON document. The app has a block renderer and a bundled default layout; it has no other layout.
2. **A block's content is inline OR bound to a live source** (`data.mode`). Inline = the JSON carries the cards. Source = the
   JSON names a feed (`poojas.upcoming`, `temples.near_me`, `panchang.today` …) and the app resolves it from the feeds it already
   loads, so live things stay live. Personal / location data (next booking, temples near me) can only be source-bound.
3. **Registries, not enums in code.** Block types and sources are listed by `GET /api/admin/home-layout/registry`; the
   dashboard builder renders its forms from it and the server validates against it. Unknown block types / sources in a newer
   layout are skipped by an older app (each type declares `minAppVersion`).
4. **Targeting is schedule + language + feature flag only** (per block). No per-user rules; the same JSON for everyone
   (cacheable, `ETag`).
5. **Fail safe.** Offline / API down / invalid JSON → last good cached layout → bundled default layout. A block that has no
   content (empty source, all items flag-hidden) is omitted, never rendered as a blank hole.
6. **Draft → publish.** Operators edit a draft; Publish makes it live and keeps history for one-click rollback.
7. **Honesty.** No invented counts/ratings; sources return real data or nothing.

## 1. Document

```jsonc
{ "schemaVersion": 1,
  "blocks": [ Block, … ] }                       // order = array order (no separate `order` field)
```

**Block** (common fields; unknown fields are rejected on save, ignored on read)
```jsonc
{ "id": "b-7f3k",                    // stable, unique in the document, never reused (generated by the dashboard)
  "type": "shelf",                   // registry key (§2)
  "enabled": true,
  "startsAt": null, "endsAt": null,  // ISO, null = open-ended
  "language": "all",                 // "all" | "en" | "hi" — shown only when the app language matches (server filters on ?lang)
  "flag": "",                        // feature-flag key; the block is hidden while flags[flag] === false (unknown flag = shown)
  "title": "", "titleHi": "", "subtitle": "", "subtitleHi": "",
  "tone": "",                        // "" | gold | purple | crimson | forest | maroon
  "action": null,                    // Action | null  — "see all" / footer / whole-block tap, per type
  "actionLabel": "", "actionLabelHi": "",
  "props": { },                      // per-type options (§2), validated by the type
  "data": null }                     // Data | null (§3), per-type
```

**Action** `{ "type": "pooja"|"chadhava"|"temple"|"bhajan"|"astrologer"|"coins"|"event"|"live"|"panchang"|"horoscope"|"events"|"route"|"link"|"none", "ref": "<slug | in-app path | https url>" }`.
The SERVER resolves every action to an `href` on read (`pooja`→`/pooja/<ref>`, `chadhava`→`/chadhava/<ref>`, `temple`→`/poojas?temple=<ref>`, `bhajan`→`/bhajan`, `astrologer`→`/astrologers`, `coins`→`/wallet`, `event`→`/events/<ref>`, `events`→`/events`, `live`→`/darshan` (or `/darshan/<ref>`), `panchang`→`/panchang`, `horoscope`→`/horoscope`, `route`→`<ref>` (must start with `/`), `link`→`<ref>` (https only), `none`→`""`) — reuse the hero resolver. Public blocks/items therefore carry `action` AND `href`.

**Data** — `{ "mode": "inline", "items": [Item, …] }` or `{ "mode": "source", "source": "<key>", "params": {}, "limit": 6 }` (`limit` 1..20, optional).
**Item** `{ "title","titleHi","subtitle","subtitleHi","icon","image","badge": ""|"new"|"soon"|"special","liveBadge": false,"flag","deitySlug","action": Action|null }` (+ server-added `href`). `liveBadge:true` shows "LIVE" while any live-darshan stream is live. `image` is `/uploads/…` or https. `icon` is an app icon name (the registry lists them).

## 2. Block types (registry v1)
`minAppVersion` is "1.0.0" for all v1 types. "data" says which modes the type allows.

| type | what it is | props | data |
|---|---|---|---|
| `header` | greeting, avatar, wallet chip, reminders bell | `showWallet` bool | none |
| `search` | search bar | `placeholder`,`placeholderHi` | none |
| `slider` | the Home slider | – | source `hero` (default, the managed `HeroSlide` collection) or inline items (`image`+`title`+`subtitle`+`action`) |
| `quick_grid` | icon tiles | `columns` 3\|4 | inline |
| `shelf` | titled shelf of cards | `layout` photo3\|book2\|list\|grid4 | inline, or source ∈ poojas.upcoming, poojas.featured, chadhava.listings, events.upcoming, events.mine, festivals.upcoming, bhajans.featured, knowledge, temples.saved |
| `deity_row` | round deity chips | – | source `deities` or inline (`deitySlug`) |
| `promo` | one banner or HTML card | `kind` banner\|html, `html`,`htmlHi` (sanitised on save and read) | inline (1 item) |
| `astrologer` | talk-to-astrologer card | – | source `astrologers.online` |
| `featured_pooja` | the featured pooja card | – | source `poojas.featured` |
| `daily` | today's darshan/aarti/panchang quick blocks | – | source `daily.today` |
| `panchang` | today's panchang card | – | source `panchang.today` |
| `rashi_row` | zodiac chips | – | source `horoscope.today` |
| `temples_near` | temples near me | – | source `temples.near_me` |
| `next_seva` | the devotee's next booking | – | source `bookings.next` (hidden when none / signed out) |
| `listen` | bhajan teaser | – | source `bhajans.featured` |
| `events` | events teaser (continue / upcoming) | – | source `events.mine` or `events.upcoming` |
| `share` | share-the-app card | `message`,`messageHi` | none |
| `html` | free sanitised HTML | `html`,`htmlHi` | none |
| `spacer` | vertical gap | `height` 4..96 | none |
| `fab` | floating button | `icon` | none (uses `title` + `action`) |

Rules: `data` mode/source must be allowed for the type (`400 bad_layout`, path in `fields`); a type with `data: none` must have `data: null`; inline `items` ≤ 24, `blocks` ≤ 60; texts ≤ 160 chars; `html` ≤ 20 KB, sanitised with the existing `html-sanitizer`.

## 3. Sources (registry v1)
`hero`, `deities`, `poojas.featured`, `poojas.upcoming`, `chadhava.listings`, `temples.near_me`, `temples.saved`, `festivals.upcoming`, `events.upcoming`, `events.mine`, `bookings.next`, `astrologers.online`, `panchang.today`, `horoscope.today`, `bhajans.featured`, `knowledge`, `daily.today`. Each entry: `{ key, title, params: schema, auth: bool, resolvedBy: "app" }`. In v1 the APP resolves every source from the feeds it already uses; `params` narrow a source (e.g. `{ "temple": "kashi-vishwanath" }` on `poojas.upcoming`, `{ "category": "<slug>" }` on `chadhava.listings`, `{ "tags": ["<tag slug>"] }` on `events.upcoming`); the registry lists each source's allowed params and unknown params are rejected. Sources marked `auth:true` are omitted for guests.

## 4. HTTP
**Public** (mounted before the gate, like `/api/live`): `GET /api/home?lang=en|hi` → `{ "version": 12, "schemaVersion": 1, "publishedAt": iso, "blocks": [Block] }` — only `enabled`, in-window, language-matching blocks (a block with `language:"hi"` is omitted for `lang=en`; no `lang` = no language filtering), `href` resolved on every action/item, `html` re-sanitised, `ETag` + `Cache-Control: public, max-age=60`, `304` on `If-None-Match`. There is ALWAYS a published layout (seeded default). `GET /api/content` keeps serving `home.sections` unchanged.
**Admin** (area `content`; editor writes, viewer reads; add to the admin-bff area tables + `access/routes.js`; writes audited):
- `GET /api/admin/home-layout` → `{ draft: {schemaVersion,blocks,updatedAt,updatedBy}, published: {version,publishedAt,publishedBy,note,blockCount}, history: [{version,publishedAt,publishedBy,note,blockCount}] (last 20), dirty: bool }`.
- `PUT /api/admin/home-layout/draft` `{schemaVersion, blocks}` → saves the draft (full validation; `400 {code:"bad_layout", fields:{"blocks.3.data.source":"…"}}`).
- `POST /api/admin/home-layout/validate` same body → `{ok:true}` or the 400 shape, saves nothing.
- `POST /api/admin/home-layout/publish` `{note?}` → publishes the (re-validated) draft as version n+1 → `{version}`.
- `POST /api/admin/home-layout/rollback` `{version}` → copies that version into the DRAFT (does not publish) → `{draft}`; `POST …/reset-default` → draft = the built-in default.
- `GET /api/admin/home-layout/versions/:n` → the stored document. `GET /api/admin/home-layout/registry` → `{ blockTypes:[{type,title,description,minAppVersion,props:<JSON-schema-ish>,data:{modes:[…],sources:[…]|null},icon}], sources:[…], actionTypes:[…], icons:[…], tones:[…], flags:[…known flag keys] }`.
- Per-version history keeps full documents (≤ 50 versions; oldest trimmed).

One identical copy lives in the catalog service (seed + "reset to default") and one bundled in the app (`features/home/constants/default-layout.json`, the offline fallback); a parity test fails if they differ. A fresh database seeds the default as version 1 (draft = published). An existing database with `HomeSection` rows gets them migrated once (idempotent).

## 6. App behaviour
`useHomeLayout()`: cached layout (AsyncStorage, per language) shown instantly → refresh from `/api/home?lang=` (ETag) → on failure keep cached → else bundled default. `HomeScreen` = `BlockList` over `blocks`: filters (`enabled`, window against `now`, `language`, `flag`), then `BLOCKS[type]` renders; unknown type or `minAppVersion` > app version → skipped. Each block component loads ITS source with the existing feed hooks only when mounted (no global fetch for absent blocks). Every tap goes through the one `useOpenHref` (https / in-app / unknown-route safe). Header/search/fab are blocks: if an operator removes them they are gone (the dashboard warns). i18n: block texts use `xxxHi` when the language is Hindi and the Hindi text is non-empty. Nothing in the app branches on a block `id` or a title.

## 7. Dashboard
Tab "Home layout" (area `content`, replaces the old sections page; "Home slider" stays): left = block list (drag or ↑↓ reorder, enable toggle, duplicate, delete, add from the registry palette), centre = a schematic **phone preview** (block cards drawn from the JSON: titles, tones, item thumbnails, hatched "live source" placeholders — it does not run the app), right = the selected block's form generated from the registry (common fields, props, data mode inline items editor or source picker + params, targeting: dates, language, flag, action picker). Second tab "JSON": the whole document in a validated editor with Format, Import, Export, copy. Draft status bar: Unsaved/Saved draft, Publish (with note), History drawer with Preview-diff (block count/changed ids) and Roll back to draft. Viewers: read-only. Validation errors from `bad_layout.fields` map to the exact block/field.

## 8. Implementation notes (backend, as built)
Code: `backend/services/catalog/src/modules/home/` (`registry.js`, `layout.validate.js`, `layout.public.js`, `layout.routes.js`, `layout.seed.js`, `layout.store.js`, `layout.model.js`); edges in `packages/common` (`catalog-mount.js` for `GET /api/home`, `catalog-routes.js` + `access/routes.js` for the admin routes). Where this differs from, or pins down, the text above:
- **Normalisation.** Only `id` and `type` are required on a block; every other common field is filled with its default on save (`enabled:true`, `language:"all"`, strings `""`, `action:null`, `props:{}`, `data:null`), dates become ISO strings, text is trimmed, html is sanitised. `props` are validated but defaults are NOT filled in (the registry's `default` is advisory). A source `data` gets `params:{}` if omitted. `data: null` is allowed for every type (the block then has nothing to show); a type with no data MUST have null.
- **Unknown flag keys** are accepted (format `^[A-Za-z][A-Za-z0-9_]{0,39}$`), because an unknown flag means "shown"; `registry.flags` lists the known ones (engagement's defaults plus `events`).
- **Action refs.** `route` must start with a single `/`, `link` must be https; other types: empty or `[\w.-]{1,120}`. An empty ref resolves to the list screen: `pooja`->`/poojas`, `temple`->`/temples`, `chadhava`->`/chadhava`, `event`->`/events` (the default layout uses `chadhava` with no ref). `item.href` / `action.href` are server-added on read and REJECTED on save.
- **Item `image`** is `""`, `/uploads/<file>` or https. Inline `items` max 24 (promo: 1); `blocks` max 60; every text <= 160 chars; html <= 20 KB (bytes).
- **Response shapes pinned down.** `PUT .../draft` -> `{draft:{schemaVersion,blocks,updatedAt,updatedBy}, dirty}`; `POST .../publish` -> `{version}`; `rollback` and `reset-default` -> `{draft}`; `GET .../versions/:n` -> `{version,publishedAt,publishedBy,note,blockCount,schemaVersion,blocks}`; `history` lists the last 20 versions INCLUDING the live one, newest first. A rollback to a trimmed version is `404`. Publishing an unchanged draft is allowed (version still increments). The registry also returns `badges`, `languages` and `limits`.
- **ETag.** Weak, `W/"<sha1 of the JSON body, 20 hex>"`. Computed by catalog (internal path) and again by the mobile/admin BFF (so it holds on a stale-while-error answer); `If-None-Match` is matched by hand (weak compare, lists, `*`), so a browser reload (`Cache-Control: no-cache`) still gets its 304.
- **Seeding.** The layout seeds BEFORE the legacy `HomeSection` defaults, so a brand-new database gets the pure default (16 blocks, version 1); a database that already has enabled `custom`/`knowledge` sections gets them as `shelf` blocks (id `m-<key>`, tone/layout/items/footer kept, an item `href` becomes a `route`/`link` action, bad icons/badges are dropped, sections with no items are skipped) inserted just before `listen`, once, only while there is no layout version.
- **Dashboard note:** a draft may be saved with blocks that are "empty" (e.g. `shelf` with `data:null`); the app omits them. Publish re-validates the stored draft.

### 9.1 Document v2
```jsonc
{ "schemaVersion": 2,
  "layouts": [ Layout, … ] }          // ≤ 8. Array order = PRIORITY (first match wins); the layout with id "default" is the fallback
```
**Layout** `{ id (slug, unique, stable), name (1–40 chars), enabled: bool, audience: [segment…] (empty = everyone), startsAt: iso|null, endsAt: iso|null, blocks: [Block…] }`. Exactly one layout has `id:"default"`: it has no `audience`, no schedule, `enabled:true`, cannot be deleted, and is the fallback when nothing else matches. A new layout may be created as a copy of any existing one.
**Block** (additions to §1): `audience: [segment…]` (empty = everyone; ANY-of). **Item** (additions): `enabled: bool` (default true; false = "Hidden in this layout", never drawn), `badgeUntil: iso|null` (the item's `badge` is shown only until this instant; after it the badge disappears but the item stays). **Block props** (additions): `quick_grid` → `columns` 3|4|5 (default 4), `tileStyle` `"icon"|"image"|"pill"` (default `"icon"`); `quick_grid` inline items ≤ **12**. **Fixed blocks:** in EVERY layout the first two blocks are an enabled `header` then an enabled `search` (they are the design's single "Top bar and search · Fixed" row; they cannot be disabled, removed, moved or given an audience/schedule; validation `400 bad_layout`). New shelf source **`live.now`** (temples live now, cards with the temple name and LIVE chip; opens `/darshan/<slug>`; hidden when none) — the design's "Live darshan row".
**Audience segments** (registry `audiences`, closed list): `new_user` (account created ≤ 7 days ago), `has_booking` (≥ 1 non-cancelled booking), `in_event` (joined an event that is not finished), `lapsed` (the app was last opened > 14 days ago). **Evaluated ON THE DEVICE** from data the app already has (profile `createdAt`, bookings, `/me/events`, a locally stored last-open time read BEFORE it is updated at launch) — the server never learns who is who, and `GET /api/home` stays identical for everyone (cacheable). An **unknown** segment (newer server) = does not match (the block / layout is hidden), never shown to everyone. Unknown/unavailable data (offline, guest) = segment does not match.

### 9.2 Public `GET /api/home?lang=` (replaces the §4 body)
`{ "version": n, "schemaVersion": 2, "publishedAt": iso, "layouts": [ { id, name, audience, startsAt, endsAt, blocks } ] }` — only layouts that are `enabled` and whose schedule contains NOW (so a transition is seen within the 60 s cache), in priority order with `default` always present and last; each block already filtered by `enabled`, window and `language` (§4) but NOT by audience; items with `enabled:false` are removed; `href`s resolved. ETag/304/stale-while-error unchanged.
**App selection:** the first layout in the list whose `audience` matches the device (empty matches everyone), else `default`; then the block filters of §6 plus the block's own `audience`, items' `badgeUntil`.

### 9.3 Admin changes
Draft/publish/history/rollback/reset-default now act on the WHOLE set (one draft, one published version, history holds whole sets). `GET /api/admin/home-layout` → adds `changes: int` (number of differences between the draft and the published set: layouts added/removed/renamed/re-scheduled/re-audienced + per layout the blocks added/removed/moved/changed, counted by block id; 0 when equal) and `dirty` = changes > 0. New `POST /api/admin/home-layout/discard` → draft = the published set → `{draft}`. `reset-default` → the set becomes `{layouts:[default]}` with the built-in default. Registry adds: `audiences: [{key,label,description}]` (labels: "New users (first 7 days)", "Has a booking", "In an event", "Hasn't opened in 14 days"), `tileStyles`, per-type `fixed: true` for header/search, human titles matching the design (`slider` "Promo slider", `deity_row` "Deity stories", `daily` "Daily darshan", `panchang` "Aaj ka Panchang", `featured_pooja` "Festival banner", `quick_grid` "Services grid", `next_seva` "Your next seva", `events` "Your events", `temples_near` "Temples near you", `rashi_row` "Aaj ka Rashifal", `astrologer` "Talk to an astrologer", `listen` "Listen now", `share` "Share with family", `shelf` "Shelf of cards", `promo` "Banner", `html` "Custom HTML"), and a one-line `summary` template per type. Stored v1 documents (draft and versions) are upgraded to v2 on read/at boot, idempotently. `default-layout.json` (both copies, byte-identical, parity-tested) becomes the v2 document `{schemaVersion:2, layouts:[{id:"default",name:"Default layout",…,blocks}]}`.

## 10. v2.1 implementation notes (backend, as built)

Code: the same files as section 8 plus `layout.upgrade.js` (v1 -> v2) and `layout.diff.js` (the "N changes" count); the default document and its app copy are the v2 `default-layout.json`. Where this pins down or differs from section 9:
- **Document v2 validation** (`layouts.<i>...` paths): `schemaVersion` must be 2 (a v1 body is `400`, `blocks` reported as an unknown field), `layouts` 1..8 with exactly one `id:"default"`; layout `id` uses the block-id rule (letters, digits, `-`, `_`, <= 40) and is unique in the set; `name` is required, trimmed, 1..40; the default must be enabled, with no audience and no schedule; `endsAt` must be after `startsAt` (equal is refused). A layout's `blocks` <= 60 INCLUDING the two fixed ones. Block ids are unique **inside a layout** (a copied layout keeps its block ids), not across layouts. `audience` lists collapse duplicates; an unknown key is `400` (`layouts.1.blocks.3.audience.0`).
- **Fixed blocks**: `blocks[0]` must be a `header` and `blocks[1]` a `search` (paths `layouts.i.blocks.0.type` / `.1.type`), each `enabled:true`, `audience:[]`, no `startsAt`/`endsAt`, `language:"all"`; a second `header`/`search` anywhere else is refused. A `flag` on them is NOT refused (not in the contract).
- **Items**: `enabled` (default true) and `badgeUntil` (ISO or null) are always present after normalisation; the public view removes `enabled:false` items but keeps `enabled:true` and `badgeUntil` on the rest (the device applies `badgeUntil`). `quick_grid` allows <= 12 items (`...data.items`: "At most 12 items."); other types still <= 24.
- **Public body**: layouts = enabled and schedule-contains-now (non-default) in array order, then `default` last (its `audience`/schedule are forced empty/null). Layout keys: `id,name,audience,startsAt,endsAt,blocks`. The ETag now also changes when a layout's schedule crosses `now` (within the 60 s cache).
- **Registry**: `audiences:[{key,label,description}]`, `tileStyles:[{key,label}]` (`icon` "Icon + label", `image` "Image tiles", `pill` "Pills"), per block type `fixed:boolean` and `summary` (placeholders `{count}` = inline item count, `{columns}`, `{source}` = the source's registry title; the dashboard fills them and drops a part it cannot fill), `limits.layouts` = 8; `header` is titled "Top bar", `search` "Search bar", `events` "Your events"; `live.now` is a source (auth false, no params) allowed only on `shelf`.
- **Admin**: `GET /admin/home-layout` -> `{draft:{schemaVersion,layouts,updatedAt,updatedBy}, published:{version,publishedAt,publishedBy,note,blockCount,layoutCount}, history:[same summary], changes, dirty}`. `changes` counts by id: layout added/removed (1, blocks not counted again), per surviving layout renamed / enabled toggled / schedule changed / audience changed / moved in priority (1 each), and blocks added / removed / moved (the fewest blocks that must jump: one drag = 1) / changed (any field incl. items, audience, enabled). `PUT draft` -> `{draft, changes, dirty}`; `discard`, `rollback`, `reset-default` -> `{draft}`; `versions/:n` -> `{version,publishedAt,publishedBy,note,blockCount,layoutCount,schemaVersion,layouts}`. `blockCount` counts blocks across all layouts.
- **Upgrade (v1 -> v2)**: a stored `{blocks}` becomes `{schemaVersion:2, layouts:[{id:"default",name:"Default layout",...,blocks}]}`. Because v2 requires the fixed rows, the upgrade moves an existing header/search to the front (enabled, unfiltered), adds the stock ones if missing (`b-01-header` / `b-02-search`, de-duplicated against existing ids), drops extra header/search blocks and keeps the first 12 tiles of an over-long grid.
